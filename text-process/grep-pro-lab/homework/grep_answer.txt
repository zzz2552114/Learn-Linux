grep 作业答案、预期结果、命令原理、命令讲解和实践作用：增强版

审读总评：
原 Word 文档的主体方向是正确的。它已经覆盖了 grep 学习中非常关键的主线：普通搜索、行号、忽略大小写、完整单词、反向过滤、扩展正则、只输出匹配内容、上下文、计数、模式文件、递归搜索、范围控制、find 结合、缺失项审计、静默判断和 PCRE 提取。

但是，原文档还存在三个需要加强的地方。
第一，部分“非常常用但容易忽略的 grep 技巧”只作为技巧出现，没有正式题目化。例如 -F、--、-l、-H、-L、-I、-a 等。对初学者来说，只读技巧不做题，很容易看懂但不会用。
第二，进阶 1 的需求写了“忽略大小写”，但原命令如果只写 -rInE，就只有 -I、-n、-E，没有真正使用 -i。增强版答案中已经修正为 -rIinE。
第三，原题已经能覆盖常用场景的大部分，但对“整行匹配”“模式以 - 开头”“只看前 N 个匹配”“排除备份文件”“BRE 和 ERE 的差异”“用模式文件做反向过滤”这些实战高频细节还可以继续加强。

因此，本答案文件保留原来的 18 道核心题，并新增 12 道正式练习题，共 30 道。它们已经足够覆盖 grep 的日常高频用法、日志排障、配置审计、安全扫描、脚本判断和字段提取入门。

共同前提：
下面所有命令都默认已经执行题目文件中的“0. 练习环境准备”，并且当前目录是 grep-pro-lab。

1. 查找普通字符串，并显示行号

题目：
在 logs/app.log 中找出所有包含大写 ERROR 的行，并显示行号。

答案命令：
grep -n 'ERROR' logs/app.log

预期结果：
4:2026-07-03T08:00:07+09:00 ERROR api database timeout host=db01.prod.example.com duration_ms=3100
5:2026-07-03T08:00:08+09:00 ERROR payment payment failed order_id=ORD-20260703-0001 status=502
10:2026-07-03T08:03:01+09:00 ERROR api password reset token leaked? token=abcDEF123456

命令原理：
grep 的默认行为是逐行读取文件。如果某一行包含给定模式，就把整行输出。这里的模式是 ERROR，文件是 logs/app.log。-n 的作用是显示 line number，也就是匹配行在文件中的行号。

命令讲解：
grep -n 'ERROR' logs/app.log 可以拆成三部分。grep 是搜索工具；-n 要求输出行号；'ERROR' 是搜索模式；logs/app.log 是被搜索的文件。因为没有使用 -i，所以它只匹配大写 ERROR，不匹配 Error、error 或 warning。

实践作用：
这是排查日志时最基础、最高频的动作。看到应用异常时，第一步通常就是 grep -n 'ERROR' app.log。行号很重要，因为你可以根据行号继续查看上下文，也可以把准确位置发给同事或写进排障记录。

2. 忽略大小写查找登录失败

题目：
在 logs/auth.log 中找出所有登录失败记录。要求同时匹配 Failed password 和 FAILED PASSWORD。

答案命令：
grep -ni 'failed password' logs/auth.log

预期结果：
2:Jul 3 08:00:12 web01 sshd[1204]: Failed password for invalid user admin from 203.0.113.7 port 49822 ssh2
3:Jul 3 08:00:14 web01 sshd[1205]: Failed password for root from 203.0.113.7 port 49824 ssh2
8:Jul 3 08:06:00 web01 sshd[1220]: FAILED PASSWORD for invalid user test from 203.0.113.8 port 49890 ssh2
9:Jul 3 08:07:00 web01 sshd[1221]: Failed password for username_root_backup from 203.0.113.10 port 49891 ssh2

命令原理：
-i 表示 ignore case，忽略大小写。命令中的模式写成 failed password，但 grep 在比较时会把大小写差异忽略掉。因此 Failed password、FAILED PASSWORD、failed password 都能匹配。

命令讲解：
-n 显示行号，-i 忽略大小写。这里使用小写模式是为了书写方便，不是要求日志中必须小写。没有 -i 时，grep 'failed password' logs/auth.log 不会匹配 Failed password，因为大小写不同。

实践作用：
很多日志来源不统一，有的组件输出 ERROR，有的输出 Error，有的输出 error。登录失败、告警级别、异常文本也经常大小写不一致。只要你不确定大小写，就应该优先想到 grep -i。

3. 匹配完整单词，而不是普通子串

题目：
在 logs/auth.log 中找出包含完整单词 root 的行。要求不要把 username_root_backup 这种包含 root 字符串的用户名当成完整单词 root。

答案命令：
grep -nw 'root' logs/auth.log

预期结果：
3:Jul 3 08:00:14 web01 sshd[1205]: Failed password for root from 203.0.113.7 port 49824 ssh2
4:Jul 3 08:01:01 web01 sudo: deploy : TTY=pts/0 ; PWD=/home/deploy ; USER=root ; COMMAND=/bin/systemctl restart nginx
6:Jul 3 08:03:09 web01 sshd[1211]: Connection closed by authenticating user root 203.0.113.7 port 50001 [preauth]
7:Jul 3 08:05:42 web01 sudo: pam_unix(sudo:session): session opened for user root by deploy(uid=1001)

命令原理：
-w 表示 word-regexp，也就是匹配完整单词。GNU grep 中，字母、数字和下划线通常被看作单词字符。因此 username_root_backup 中的 root 两边连接着下划线和其他字母，不是独立单词。

命令讲解：
grep -n 'root' logs/auth.log 会把 username_root_backup 也找出来。grep -nw 'root' logs/auth.log 则要求 root 的左右边界符合“单词边界”条件，所以更适合查用户名 root、配置值 root、独立单词 root。

实践作用：
安全排查时，root 和包含 root 的普通字符串风险含义完全不同。查 root 用户登录、root 权限、root 命令时，-w 可以减少误报。

4. 过滤掉空行和注释行，查看有效配置

题目：
查看 conf/nginx.conf 中真正生效的配置行。要求排除空行、以 # 开头的注释行、前面有空格再接 # 的注释行。

答案命令：
grep -nvE '^[[:space:]]*($|#)' conf/nginx.conf

预期结果：
2:user www-data;
3:worker_processes auto;
4:events { worker_connections 1024; }
5:http {
7: server_tokens on;
8: include /etc/nginx/mime.types;
9: server {
10: listen 80;
11: server_name example.com www.example.com;
12: root /var/www/html;
13: location /admin { deny all; }
14: location /health { access_log off; return 200 "ok"; }
15: }
16:}

命令原理：
-v 表示反向匹配，也就是不输出匹配模式的行。-E 表示使用扩展正则。正则 ^[[:space:]]*($|#) 匹配“行首开始，可以有空白，然后要么到行尾，要么出现 #”。它覆盖了空行、顶格注释行、缩进注释行。

命令讲解：
^ 是行首。[[:space:]]* 是零个或多个空白字符。($|#) 表示“行尾或者 #”。整条正则匹配不生效的配置行，再用 -v 反过来输出真正有内容并且不是注释的行。

实践作用：
查看配置时，注释和空行会干扰判断。grep -vE '^[[:space:]]*($|#)' 是运维中查看有效配置的常用模式，适用于 nginx、ssh、systemd、prometheus 等大量文本配置。

5. 用扩展正则找 HTTP 4xx 和 5xx 请求

题目：
在 logs/access.log 中找出 HTTP 状态码为 400 到 599 的请求。要求不要匹配 200、201 这类正常状态码。

答案命令：
grep -nE '" [45][0-9]{2} ' logs/access.log

预期结果：
2:203.0.113.7 - - [03/Jul/2026:08:00:02 +0900] "GET /admin HTTP/1.1" 403 142 "-" "Mozilla/5.0"
3:198.51.100.23 - - [03/Jul/2026:08:00:03 +0900] "POST /login HTTP/1.1" 401 98 "-" "Mozilla/5.0"
4:198.51.100.23 - - [03/Jul/2026:08:00:04 +0900] "POST /login HTTP/1.1" 401 98 "-" "Mozilla/5.0"
7:203.0.113.7 - - [03/Jul/2026:08:03:12 +0900] "GET /../../etc/passwd HTTP/1.1" 400 51 "-" "sqlmap/1.7"
8:203.0.113.9 - - [03/Jul/2026:08:04:13 +0900] "GET /wp-login.php HTTP/1.1" 404 153 "-" "Mozilla/5.0"
9:203.0.113.9 - - [03/Jul/2026:08:04:20 +0900] "GET /.env HTTP/1.1" 404 153 "-" "Mozilla/5.0"
10:198.51.100.77 - - [03/Jul/2026:08:05:00 +0900] "GET /api/v1/orders HTTP/1.1" 500 35 "-" "Mozilla/5.0"
11:198.51.100.77 - - [03/Jul/2026:08:05:01 +0900] "GET /api/v1/orders HTTP/1.1" 502 35 "-" "Mozilla/5.0"
12:10.0.0.5 - - [03/Jul/2026:08:05:03 +0900] "GET /health HTTP/1.1" 500 19 "-" "kube-probe/1.29"

命令原理：
-E 启用扩展正则。[45] 表示第一位是 4 或 5。[0-9]{2} 表示后面还有两位数字。前面的 " 和空格用于限定状态码字段，后面的空格用于避免把响应大小、时间、IP 或 User-Agent 里的数字误判为状态码。

命令讲解：
如果只写 grep -E '[45][0-9]{2}' logs/access.log，可能匹配到端口、时间、响应大小或其他数字。这里写成 '" [45][0-9]{2} '，利用 access log 中请求字段结束后紧跟状态码的格式，精准度更高。

实践作用：
Web 排障经常先筛 4xx 和 5xx。4xx 常见于权限、路径、参数或攻击扫描；5xx 常见于后端异常、网关错误、依赖超时。这个题训练的是“按字段写正则”，不是随便搜数字。

6. 只输出匹配内容：提取 IP 地址

题目：
从 logs/access.log 中提取所有 IPv4 地址。要求只输出 IP 本身，不输出整行。

答案命令：
grep -oE '([0-9]{1,3}\.){3}[0-9]{1,3}' logs/access.log

预期结果：
192.168.1.10
203.0.113.7
198.51.100.23
198.51.100.23
10.0.0.5
192.168.1.10
203.0.113.7
203.0.113.9
203.0.113.9
198.51.100.77
198.51.100.77
10.0.0.5

命令原理：
-o 表示 only matching，只输出匹配到的部分，而不是整行。正则 ([0-9]{1,3}\.){3}[0-9]{1,3} 表示“三段数字加点号，再加最后一段数字”。点号在正则中本来表示任意字符，所以要写成 \. 才表示真正的点。

命令讲解：
[0-9]{1,3} 匹配 1 到 3 位数字。([0-9]{1,3}\.){3} 匹配三次“数字加点”。最后的 [0-9]{1,3} 匹配最后一段。这个正则用于提取“长得像 IPv4 的字符串”，不用于严格校验每段是否在 0 到 255 之间。

实践作用：
你经常需要从日志中提取 IP、订单号、状态码、请求 ID、token 片段。只要目标是“提取字段”，就应该想到 grep -o。

7. 多关键词匹配：查找错误、超时、OOM

题目：
在 logs/app.log 中找出包含以下任意一种问题的行：ERROR、FATAL、timeout、out of memory。

答案命令一：
grep -nE 'ERROR|FATAL|timeout|out of memory' logs/app.log

答案命令二：
grep -n -e 'ERROR' -e 'FATAL' -e 'timeout' -e 'out of memory' logs/app.log

预期结果：
4:2026-07-03T08:00:07+09:00 ERROR api database timeout host=db01.prod.example.com duration_ms=3100
5:2026-07-03T08:00:08+09:00 ERROR payment payment failed order_id=ORD-20260703-0001 status=502
8:2026-07-03T08:02:10+09:00 FATAL worker out of memory pid=2222
10:2026-07-03T08:03:01+09:00 ERROR api password reset token leaked? token=abcDEF123456

命令原理：
使用 -E 时，| 表示“或者”。ERROR|FATAL|timeout|out of memory 表示任意一个模式匹配即可。多个 -e 也表示提供多个模式，任意模式命中就输出该行。

命令讲解：
少量短关键词可以用 grep -E 'A|B|C'。关键词较长、包含特殊字符、来自脚本变量或需要动态拼接时，多个 -e 更清晰，也更不容易因为 | 的优先级或转义问题出错。

实践作用：
故障排查时很少只查一个词。你可能同时关注 ERROR、FATAL、timeout、refused、OOM、BackOff。多关键词搜索可以迅速扩大故障线索范围。

8. 查看错误上下文

题目：
在 logs/app.log 中找到 FATAL 所在行，并显示它前后各 2 行。

答案命令：
grep -nC 2 'FATAL' logs/app.log

预期结果：
6-2026-07-03T08:00:09+09:00 INFO api health check ok status=200
7-2026-07-03T08:01:10+09:00 warning worker disk space low mount=/var usage=86%
8:2026-07-03T08:02:10+09:00 FATAL worker out of memory pid=2222
9-2026-07-03T08:02:11+09:00 TRACE api request_id=abc-123 path=/api/v1/orders
10-2026-07-03T08:03:01+09:00 ERROR api password reset token leaked? token=abcDEF123456

命令原理：
-C 是 context，表示同时显示匹配行前后的上下文。-C 2 表示前 2 行和后 2 行。-n 显示行号。GNU grep 在上下文输出中，匹配行前面通常用冒号，非匹配上下文行前面通常用连字符。

命令讲解：
单独看到 FATAL worker out of memory 只能知道发生了严重问题。加上 -C 2 后，你能看到前面有 warning worker disk space low，后面还有 TRACE 和 ERROR。这能帮助判断事故前后发生了什么。

实践作用：
日志排查不能只看命中的一行。真正的原因经常在错误前几行，恢复或连锁反应经常在错误后几行。-A、-B、-C 是 grep 排障能力的核心。

9. 统计每个文件里匹配了多少行

题目：
统计 logs/app.log、logs/kubelet.log 中每个文件包含 ERROR 或 FATAL 的行数。

答案命令：
grep -cE 'ERROR|FATAL' logs/app.log logs/kubelet.log

预期结果：
logs/app.log:4
logs/kubelet.log:0

命令原理：
-c 表示 count，只输出匹配行数量，不输出匹配行内容。-E 使用扩展正则，ERROR|FATAL 表示匹配 ERROR 或 FATAL。

命令讲解：
logs/app.log 中有三行 ERROR 和一行 FATAL，所以结果是 4。logs/kubelet.log 中有 Error syncing pod，但没有大写 ERROR，也没有 FATAL，所以结果是 0。如果要忽略大小写，可以写 grep -ciE 'error|fatal' logs/app.log logs/kubelet.log。

实践作用：
排障不只是“有没有错误”，还要看“错误数量是多少”“哪个文件更多”“是否突然暴增”。grep -c 是最基础的文本统计入口。

10. 使用模式文件批量匹配

题目：
使用 patterns/errors.patterns 作为模式文件，在 logs/ 目录下搜索错误关键词。要求显示文件名和行号。

答案命令：
grep -R -nH -f patterns/errors.patterns logs/

预期结果：
logs/app.log:4:2026-07-03T08:00:07+09:00 ERROR api database timeout host=db01.prod.example.com duration_ms=3100
logs/app.log:5:2026-07-03T08:00:08+09:00 ERROR payment payment failed order_id=ORD-20260703-0001 status=502
logs/app.log:8:2026-07-03T08:02:10+09:00 FATAL worker out of memory pid=2222
logs/app.log:10:2026-07-03T08:03:01+09:00 ERROR api password reset token leaked? token=abcDEF123456
logs/kubelet.log:2:Jul 03 08:00:05 node01 kubelet[778]: W0703 Back-off restarting failed container payment
logs/kubelet.log:5:Jul 03 08:02:10 node01 kubelet[778]: E0703 ImagePullBackOff for image registry.example.com/private/payment:2.1.0

命令原理：
-f patterns/errors.patterns 表示从文件读取模式，一行一个模式。-R 递归搜索目录。-n 显示行号。-H 强制显示文件名。

命令讲解：
模式文件中有 ERROR、FATAL、timeout、ImagePullBackOff、Back-off。grep 会把这些模式逐个用于匹配，只要一行命中任意模式，就输出这一行。注意 -R 会递归目录，并且会跟随递归过程中遇到的符号链接；如果不想跟随所有符号链接，一般使用 -r。

实践作用：
真实运维中，错误关键词、安全特征、敏感字段、忽略规则经常很多。把它们写进模式文件，比把十几个词硬塞进一条命令更清晰、更可维护。

11. 递归搜索项目，但排除 archive 和 vendor

题目：
在整个项目中搜索疑似敏感信息：PASSWORD、TOKEN、API_KEY、DATABASE_URL、JWT_SECRET、secret。要求递归搜索、显示文件名和行号、忽略大小写、排除 archive 目录、排除 vendor 目录，只搜索 .log、.env、.py、.js、.md 文件。

答案命令：
grep -rIinE \
 --include='*.log' \
 --include='*.env' \
 --include='*.py' \
 --include='*.js' \
 --include='*.md' \
 --exclude-dir=archive \
 --exclude-dir=vendor \
 'password|token|api_key|database_url|jwt_secret|secret' .

预期结果：
./logs/app.log:10:2026-07-03T08:03:01+09:00 ERROR api password reset token leaked? token=abcDEF123456
./logs/auth.log:2:Jul 3 08:00:12 web01 sshd[1204]: Failed password for invalid user admin from 203.0.113.7 port 49822 ssh2
./logs/auth.log:3:Jul 3 08:00:14 web01 sshd[1205]: Failed password for root from 203.0.113.7 port 49824 ssh2
./logs/auth.log:8:Jul 3 08:06:00 web01 sshd[1220]: FAILED PASSWORD for invalid user test from 203.0.113.8 port 49890 ssh2
./logs/auth.log:9:Jul 3 08:07:00 web01 sshd[1221]: Failed password for username_root_backup from 203.0.113.10 port 49891 ssh2
./conf/app.env:4:DATABASE_URL=postgres://app:secret@db01.prod.example.com:5432/app
./conf/app.env:6:API_KEY=sk_live_demo_123456
./conf/app.env:7:TOKEN=abcDEF123456
./src/app.py:4:# TODO: move this to a secret manager
./src/app.py:5:DEFAULT_PASSWORD = "demo-password"
./src/auth.js:1:const jwtSecret = process.env.JWT_SECRET;
./src/auth.js:4:function login(user, password) {
./docs/runbook.md:5:Look for ERROR, FATAL, timeout, ImagePullBackOff, and Failed password.
./docs/runbook.md:7:Do not paste DATABASE_URL, API_KEY, TOKEN, PASSWORD, or JWT_SECRET into tickets.

命令原理：
-r 递归搜索目录。-I 把二进制文件视为不匹配，减少乱码。-i 忽略大小写。-n 显示行号。-E 使用扩展正则。--include 控制只搜索哪些文件名模式。--exclude-dir 排除目录。

命令讲解：
这里必须有 -i，因为题目要求忽略大小写。只写 -rInE 时，-I 是二进制处理，-n 是行号，-E 是扩展正则，并没有忽略大小写。增强版改成 -rIinE，才能匹配 API_KEY、TOKEN、DATABASE_URL、JWT_SECRET、FAILED PASSWORD 等大小写不同的文本。

实践作用：
敏感信息扫描不能粗暴地 grep -r 'password' .。真实项目里有 archive、vendor、node_modules、build、dist、tmp 等大量噪音目录。高质量的 grep 命令必须同时控制关键词、大小写、文件类型和搜索范围。

12. 审计 SSH 危险配置

题目：
检查 conf/sshd_config 中是否存在未注释的危险配置：PermitRootLogin yes、PasswordAuthentication yes。要求不要匹配注释行，允许配置项前面有空格，允许配置项和值之间有多个空格或 Tab，显示行号。

答案命令：
grep -nE '^[[:space:]]*(PermitRootLogin|PasswordAuthentication)[[:space:]]+yes([[:space:]]*)?$' conf/sshd_config

预期结果：
2:PermitRootLogin yes
3:PasswordAuthentication yes

命令原理：
^ 从行首开始。[[:space:]]* 允许开头有空格或 Tab。(PermitRootLogin|PasswordAuthentication) 匹配两个配置项之一。[[:space:]]+ 要求配置项和值之间至少有一个空白。yes 匹配危险值。([[:space:]]*)?$ 允许行尾有空白，然后结束。

命令讲解：
这条命令不会匹配 #PermitRootLogin prohibit-password，因为正则要求行首空白后马上出现配置项，而注释行空白后是 #。这比 grep 'PermitRootLogin' conf/sshd_config 更严谨。

实践作用：
配置审计必须区分“出现过”和“真正生效”。注释里的配置、文档示例、历史残留不应该被当成风险项。这个题训练的是未注释配置审计的标准写法。

13. 审计 Nginx 是否暴露版本号

题目：
检查 conf/nginx.conf 里是否存在生效的 server_tokens on;。要求不要匹配注释行，允许前面有缩进，允许 on 后面有空格再接分号，显示行号。

答案命令：
grep -nE '^[[:space:]]*server_tokens[[:space:]]+on[[:space:]]*;' conf/nginx.conf

预期结果：
7: server_tokens on;

命令原理：
^[[:space:]]* 匹配行首缩进。server_tokens 匹配配置项。[[:space:]]+ 匹配配置项和值之间的空白。on 匹配危险值。[[:space:]]*; 允许 on 和分号之间有空白。

命令讲解：
它不会匹配第 6 行的 # server_tokens off;，因为第 6 行缩进后是 #，不是 server_tokens。这个命令只关注真正可能生效的配置行。

实践作用：
server_tokens on; 会暴露 Nginx 版本信息，可能增加攻击者收集指纹的便利。安全审计时应检查它是否处于生效状态，而不是只检查文本中有没有 server_tokens 这个词。

14. 只看真实业务 5xx，排除健康检查

题目：
从 logs/access.log 中找出 HTTP 5xx 请求，但排除 /health 健康检查请求。要求只使用 grep，可以使用管道，显示行号。

答案命令：
grep -nE '" 5[0-9]{2} ' logs/access.log | grep -v '/health '

预期结果：
10:198.51.100.77 - - [03/Jul/2026:08:05:00 +0900] "GET /api/v1/orders HTTP/1.1" 500 35 "-" "Mozilla/5.0"
11:198.51.100.77 - - [03/Jul/2026:08:05:01 +0900] "GET /api/v1/orders HTTP/1.1" 502 35 "-" "Mozilla/5.0"

命令原理：
第一段 grep -nE '" 5[0-9]{2} ' 找出所有 5xx。管道 | 把第一段输出交给第二段。第二段 grep -v '/health ' 反向过滤掉健康检查请求。

命令讲解：
grep 管道常用来表达逻辑组合。包含 A 且不包含 B，可以写成 grep 'A' file | grep -v 'B'。这里 A 是 HTTP 5xx，B 是 /health。

实践作用：
生产日志中健康检查、探针、负载均衡器检测、监控请求经常制造噪音。排查真实用户请求时，先排除 /health、kube-probe、ELB-HealthChecker 一类噪音非常重要。

15. 使用 find -exec grep 搜索指定类型文件

题目：
在 conf/ 和 src/ 目录下，只搜索普通文件，找出包含 TODO、FIXME、PASSWORD、JWT_SECRET 的行。要求结合 find，不要使用 xargs，不要使用 sed，不要使用 awk，显示文件名和行号。

答案命令：
find conf src -type f -exec grep -nHE 'TODO|FIXME|PASSWORD|JWT_SECRET' {} +

预期结果：
src/app.py:4:# TODO: move this to a secret manager
src/app.py:5:DEFAULT_PASSWORD = "demo-password"
src/auth.js:1:const jwtSecret = process.env.JWT_SECRET;
src/auth.js:3:// FIXME: temporary debug bypass

命令原理：
find conf src -type f 先找出 conf 和 src 目录下的普通文件。-exec grep ... {} + 把找到的文件批量交给 grep。{} 代表 find 找到的文件。+ 表示尽量把多个文件合并到一次 grep 调用中。

命令讲解：
-n 显示行号，-H 显示文件名，-E 使用扩展正则。TODO|FIXME|PASSWORD|JWT_SECRET 表示四种模式任意一种。这里没有使用 -i，所以 jwtSecret 中的小写 jwt 不会因为 jwt 这部分匹配，真正命中的是 JWT_SECRET。

实践作用：
grep -r 很方便，但 find 更适合先精确筛文件，例如只筛普通文件、按修改时间筛、按大小筛、按路径深度筛。find -exec grep ... {} + 是运维和开发排查中非常稳的组合。

16. 找出缺少安全配置的文件

题目：
在 conf/ 下找出不包含 PasswordAuthentication no 的文件。要求只输出文件名，可以结合 find，不要使用 sed、awk。

答案命令一：
grep -L 'PasswordAuthentication no' conf/*

预期结果一：
conf/app.env
conf/app.env.bak
conf/jvm.options
conf/nginx.conf
conf/prometheus.yml
conf/sshd_config

答案命令二：
find conf -type f -exec grep -L 'PasswordAuthentication no' {} +

预期结果二：
conf/app.env
conf/app.env.bak
conf/sshd_config
conf/nginx.conf
conf/prometheus.yml
conf/jvm.options

命令原理：
-L 表示列出没有匹配内容的文件名。它和 -l 相反。-l 列出包含匹配内容的文件，-L 列出不包含匹配内容的文件。

命令讲解：
conf/ 下所有文件都不包含 PasswordAuthentication no，所以都会被列出。第一种写法依赖 shell 展开 conf/*。第二种写法用 find -type f 明确只处理普通文件，更适合目录层级复杂时使用。两种写法输出顺序可能不同，这是正常现象。

实践作用：
很多审计任务是找“缺少必须配置”的文件，而不是找“包含危险配置”的文件。例如缺少 PasswordAuthentication no、缺少 server_tokens off、缺少 Restart=always、缺少 APP_ENV=prod。这时 grep -L 很有用。

17. 在脚本里用 grep 判断是否危险

题目：
判断 conf/sshd_config 是否存在未注释的 PermitRootLogin yes。如果存在，输出 unsafe；如果不存在，输出 ok。要求 grep 本身不要输出匹配行，只根据退出码判断。

答案命令：
grep -qE '^[[:space:]]*PermitRootLogin[[:space:]]+yes([[:space:]]*)?$' conf/sshd_config && echo unsafe || echo ok

预期结果：
unsafe

命令原理：
-q 表示 quiet，静默模式。grep 不输出匹配行，只通过退出码表达结果。匹配到通常返回 0，没有匹配到返回 1，发生错误返回 2。shell 中 && 表示前一个命令成功才执行后一个命令，|| 表示前一个命令失败才执行后一个命令。

命令讲解：
如果 grep 匹配到未注释的 PermitRootLogin yes，退出码是 0，于是执行 echo unsafe。如果没有匹配到，grep 退出码是 1，于是执行 echo ok。

实践作用：
grep -q 是脚本里最常用的 grep 用法之一。它适合做条件判断、健康检查、CI 检查、安全基线检查和自动化部署前检查。

18. 使用 PCRE 精确提取字段

题目：
从 logs/access.log 中只提取 HTTP 状态码数字。要求输出 200、403、401 等状态码，不要输出引号、空格、响应大小或整行。

答案命令：
grep -oP '(?<=" )[0-9]{3}(?= [0-9]+ )' logs/access.log

预期结果：
200
403
401
401
200
200
400
404
404
500
502
500

命令原理：
-P 使用 PCRE，也就是 Perl Compatible Regular Expression。-o 只输出匹配部分。(?<=" ) 是正向后顾，要求状态码前面必须是双引号和空格，但不把它输出。(?= [0-9]+ ) 是正向前瞻，要求状态码后面必须是空格、响应大小、空格，但也不输出。

命令讲解：
[0-9]{3} 才是真正输出的状态码。前后顾只是限定位置。这个写法比基础正则更精确，但依赖 GNU grep 的 PCRE 支持。

实践作用：
需要精确提取字段且不想输出分隔符时，grep -P 很方便。不过日常应先掌握 grep、grep -E、grep -F；只有确实需要 lookbehind、lookahead、\K 等能力时，再使用 grep -P。

19. 使用固定字符串搜索，避免正则元字符误伤

题目：
分别在 src/app.py 和 docs/release-notes.txt 中搜索普通字符串 https://api.example.com/v1 和 a.b[c]。要求把点号、方括号等字符都当普通字符处理，不当正则处理。

答案命令一：
grep -nF 'https://api.example.com/v1' src/app.py

预期结果一：
2:API_ENDPOINT = "https://api.example.com/v1"

答案命令二：
grep -nF 'a.b[c]' docs/release-notes.txt

预期结果二：
3:Known issue: a.b[c] appears in debug examples.

命令原理：
-F 表示 fixed strings，固定字符串模式。在 -F 模式下，.、?、[、]、*、+、|、() 等字符都不会被当成正则元字符，而是按普通字符逐字匹配。

命令讲解：
如果搜索 URL、路径、配置片段、JSON 片段、带方括号的日志文本，很多字符在正则里有特殊含义。使用 -F 可以避免误匹配，也能减少转义负担。

实践作用：
当你的目标不是“写正则”，而是“精确查一个普通字符串”时，优先使用 grep -F。它尤其适合查 URL、文件路径、异常栈片段、固定错误消息和带特殊符号的配置值。

20. 搜索以连字符开头的模式

题目：
在 conf/jvm.options 中搜索 -Xmx。要求 -Xmx 被当作搜索模式，不被 grep 当作命令选项。

答案命令：
grep -n -- '-Xmx' conf/jvm.options

预期结果：
2:-Xmx1024m

命令原理：
-- 表示选项结束。它告诉 grep：后面的内容不再解释为选项，即使以 - 开头，也要当作普通参数。这里 '-Xmx' 因此被当作搜索模式。

命令讲解：
如果直接写 grep -n '-Xmx' conf/jvm.options，grep 可能把 -Xmx 当作选项解析，从而报错。加上 -- 后，命令结构变成：选项是 -n，选项结束，然后搜索模式是 -Xmx，文件是 conf/jvm.options。

实践作用：
很多配置项以 - 开头，例如 JVM 参数 -Xmx、curl 参数 --connect-timeout、命令行标志 --debug。搜索这类内容时，要记得使用 --。

21. 整行匹配配置项

题目：
在 conf/app.env 中查找整行等于 DEBUG=false 的行。要求不要只匹配包含 DEBUG=false 的更长行。

答案命令：
grep -nx 'DEBUG=false' conf/app.env

预期结果：
2:DEBUG=false

命令原理：
-x 表示 line-regexp，要求整个行完整匹配模式，而不是只要行内包含模式即可。-n 显示行号。

命令讲解：
grep -n 'DEBUG=false' conf/app.env 只要求包含 DEBUG=false。如果某行是 OLD_DEBUG=false 或 DEBUG=false_backup，也可能产生误判。grep -nx 'DEBUG=false' conf/app.env 要求整行正好就是 DEBUG=false。

实践作用：
配置审计经常需要判断某个配置行是否精确存在。比如 APP_ENV=prod、DEBUG=false、PasswordAuthentication no。整行匹配比普通包含匹配更严谨。

22. 只列出包含 TODO 或 FIXME 的文件名

题目：
在 src/ 和 docs/ 目录中找出包含 TODO 或 FIXME 的文件。要求只输出文件名，不输出匹配行内容。

答案命令：
grep -rlE 'TODO|FIXME' src docs

预期结果：
src/app.py
src/auth.js

命令原理：
-r 递归搜索目录。-l 表示 files-with-matches，只列出至少包含一个匹配项的文件名。-E 使用扩展正则，TODO|FIXME 表示匹配 TODO 或 FIXME。

命令讲解：
如果你只关心“哪些文件有 TODO 或 FIXME”，不关心具体是哪一行，就使用 -l。grep 在某个文件命中后，只输出文件名，通常不需要继续输出这个文件里的所有匹配行。

实践作用：
代码审查、上线前检查、技术债盘点时，经常需要先定位问题文件列表。grep -l 可以让输出更短、更适合交给后续流程处理。

23. 只看前两个 ERROR

题目：
在 logs/app.log 中只显示前两个包含 ERROR 的匹配行，并显示行号。

答案命令：
grep -nm 2 'ERROR' logs/app.log

预期结果：
4:2026-07-03T08:00:07+09:00 ERROR api database timeout host=db01.prod.example.com duration_ms=3100
5:2026-07-03T08:00:08+09:00 ERROR payment payment failed order_id=ORD-20260703-0001 status=502

命令原理：
-m 2 表示最多输出 2 个匹配行。-n 显示行号。grep 找到指定数量的匹配后会停止读取该文件。

grep -n 'ERROR' logs/app.log 会输出所有 ERROR。grep -nm 2 'ERROR' logs/app.log 只输出前两个。-m 对大文件非常有价值，因为它可以避免无意义地扫描完整文件。

24. 分别显示匹配行之前和之后的上下文

题目：
在 logs/kubelet.log 中找到 ImagePullBackOff，并显示它前 1 行、后 2 行。

答案命令：
grep -nB 1 -A 2 'ImagePullBackOff' logs/kubelet.log

预期结果：
4-Jul 03 08:01:09 node01 kubelet[778]: I0703 Readiness probe succeeded for pod api
5:Jul 03 08:02:10 node01 kubelet[778]: E0703 ImagePullBackOff for image registry.example.com/private/payment:2.1.0

命令原理：
-B 1 表示 before，显示匹配行之前 1 行。-A 2 表示 after，显示匹配行之后 2 行。-n 显示行号。因为 ImagePullBackOff 是文件最后一行，后面没有更多内容，所以实际只显示了前 1 行和匹配行。

命令讲解：
-C 是前后同样数量的上下文。-A 和 -B 可以不对称地控制上下文。例如你只关心错误发生前的准备阶段，就多用 -B；关心错误后的恢复行为，就多用 -A。

实践作用：
Kubernetes、systemd、应用日志经常需要看事件前后。ImagePullBackOff 前面可能有拉取镜像失败、认证失败、网络失败等信息。上下文能帮助你从“看到错误”走向“理解错误链路”。

25. 递归搜索时排除备份文件

题目：
在 conf/ 下搜索 API_KEY。要求搜索 .env 和 .env.bak 这类文件名，但排除所有 .bak 备份文件，只显示真实配置文件中的结果。

26. 用多个 grep 表达“同时满足两个条件”

题目：
从 logs/access.log 中找出请求路径为 POST /login 且 HTTP 状态码为 401 的行。要求只使用 grep 和管道。

预期结果：
3:198.51.100.23 - - [03/Jul/2026:08:00:03 +0900] "POST /login HTTP/1.1" 401 98 "-" "Mozilla/5.0"
4:198.51.100.23 - - [03/Jul/2026:08:00:04 +0900] "POST /login HTTP/1.1" 401 98 "-" "Mozilla/5.0"

命令原理：
第一个 grep 先筛出包含 POST /login 的行。管道把结果传给第二个 grep。第二个 grep 再筛出包含空格 401 空格的行。两个 grep 串联就表达了“同时满足两个条件”。

这里写 ' 401 ' 而不是 '401'，是为了把 401 当作字段匹配，减少误匹配其他数字的概率。如果要进一步严谨，可以结合请求字段和状态码字段写更完整的正则。

grep 没有 SQL 那样的 WHERE A AND B 语法，但管道可以自然表达 AND。排查登录失败、某接口报错、某用户请求、某状态码组合时，这种写法非常常见。

27. 用多个 grep 组合筛选结构化文本字段

28. 搜索多个文件时隐藏不存在文件的报错

同时在 conf/app.env 和 conf/not-exist.env 中搜索 APP_ENV。要求不存在的 conf/not-exist.env 不产生错误信息，仍然显示存在文件中的匹配结果。

29. 区分 BRE 和 ERE：同一个逻辑的两种写法

题目：
在 logs/app.log 中找出 status=200 或 status=201 的行。要求分别写出 grep -E 的写法，以及不使用 -E 时 GNU grep 基本正则风格的写法。

答案命令一，扩展正则写法：
grep -nE 'status=(200|201)' logs/app.log

预期结果一：
6:2026-07-03T08:00:09+09:00 INFO api health check ok status=200
11:2026-07-03T08:04:00+09:00 INFO api request completed status=201 duration_ms=88

答案命令二，GNU grep 基本正则写法：
grep -n 'status=\(200\|201\)' logs/app.log

预期结果二：
6:2026-07-03T08:00:09+09:00 INFO api health check ok status=200
11:2026-07-03T08:04:00+09:00 INFO api request completed status=201 duration_ms=88

命令原理：
grep 默认使用基本正则表达式 BRE。grep -E 使用扩展正则表达式 ERE。在 ERE 中，() 和 | 可以直接表达分组和或关系。在 GNU grep 的 BRE 风格中，分组和或关系通常要写成 \( \) 和 \|。

命令讲解：
grep -nE 'status=(200|201)' 更直观。grep -n 'status=\(200\|201\)' 更接近 GNU grep 默认模式下的写法。如果你忘记 -E，又写 grep -n 'status=(200|201)' logs/app.log，通常不会得到想要的结果，因为括号和竖线会被按普通字符或不同规则理解。

实践作用：
初学者常见错误是把扩展正则写法直接丢给默认 grep。建议日常凡是用到 |、+、?、{}、() 这类扩展正则能力时，就明确写 grep -E，减少歧义。

30. 使用模式文件反向过滤安全噪音

题目：
使用 patterns/security.patterns 作为排除规则，从 logs/access.log 中过滤掉明显安全扫描或攻击特征行。要求不要使用 sed、awk，只使用 grep。

答案命令：
grep -vF -f patterns/security.patterns logs/access.log

命令原理：
-f patterns/security.patterns 从模式文件读取多条规则。-F 把这些规则都当固定字符串处理，不按正则解释。-v 反向匹配，表示输出不包含这些安全特征的行。

命令讲解：
patterns/security.patterns 中包含 /../../etc/passwd、/.env、/wp-login.php、sqlmap 等明显攻击或扫描特征。grep -vF -f 会把包含这些固定字符串的行过滤掉。这里使用 -F 很重要，因为 /、. 等字符不需要作为正则解释，只需要按字面量匹配。

实践作用：
有时你不是要找攻击流量，而是要从混杂日志中排除已知扫描噪音，保留需要继续观察的业务请求。把排除规则维护在文件里，可以让规则更清晰，也方便团队复用。

最终学习建议：
第一阶段必须熟练：grep、grep -n、grep -i、grep -v、grep -w。

第三阶段必须熟练：grep -A、grep -B、grep -C、grep -f、grep -r、--include、--exclude、--exclude-dir。
第四阶段必须熟练：grep -q、grep -m、grep -x、grep -- '-pattern'、find -exec grep、grep -P。

真正掌握 grep，不是会背选项，而是能在大量文本中精确回答四类问题：哪些行符合条件，哪些文件符合条件，哪些字段需要提取，哪些噪音应该排除。
